## Корневая причина

### Цепочка деградации

```
1. Нет swap на сервере (0 MB)
2. 3 PostgreSQL инстанса без memory limits
3. Каждый HTTP-запрос открывает 2-5 сессий БД
4. Пул соединений растёт → PostgreSQL жрёт RAM
5. OOM-killer убивает бэкенд PostgreSQL (signal 9)
6. PostgreSQL postmaster перезапускает дочерние процессы
7. СТАРЫЕ процессы не умирают — остаются зомби
8. Один зомби (4116670) зациклился на 326% CPU
9. Другие зомби держат память
10. Даже без трафика: зомби жрут CPU, load average растёт
```

### Почему pool config не помог

`pool_recycle=1800` + `pool_pre_ping=True` предотвращают НАКОПЛЕНИЕ новых соединений. Но **зомби-процессы от предыдущих OOM-циклов уже существуют** и продолжают потреблять CPU/RAM независимо от новых соединений.

## Процесс 4116670 — детали

```
PID: 4116670
Команда: postgres
CPU: 326%
RSS: 2.35 GB (29.6% RAM)
Возраст: 2+ часа
В pg_stat_activity: НЕТ (отсоединён от БД)
Стек ядра: пустой (чистый userspace CPU)
```

Процесс находится в бесконечном цикле в userspace. Вероятная причина: повреждённое состояние после OOM-kill родительского бэкенда. Единственное решение — принудительное завершение (`kill -9`).

## Решение

### Срочно
1. ~~`kill -9 4116670` — не сработал. Процесс в состоянии S (sleeping), не реагирует на сигналы.~~  
   **Выполнено:** `docker restart ticketbot-db` — контейнер перезапущен, все зомби уничтожены.
2. После рестарта: load average 4.45 (↓ от 5.22), RAM free 3.0 GB (↑ от 516 MB), ticketbot-db 0.03% CPU.

### Среднесрочно
1. Добавить swap (2 GB) — предотвратит OOM-kill
2. Установить `memory: 3G` лимит на `ticketbot-db` контейнер
3. Остановить `ticketbot-dev-db` + `ticketbot-dev-web` если не нужны
